## 题型一：选择题（约 30 分）

### 1.1 架构风格识别（必拿 10 分）

**看图/关键词判风格：**

| 风格 | 识别特征（图/文字） |
|------|---------------------|
| **Batch Sequential 批处理** | 多步流水线；每步独立程序；**前步结束才下一步**；数据**整体**传递 |
| **Pipe-Filter 管道-过滤器** | 过滤器 + 管道；过滤器**独立**；数据经管道流动；可并发、可反馈环 |
| **Main/Subroutine 主从** | 主程序调用子程序；显式数据共享；单线程、结构化 |
| **面向对象 OO** | 对象 + 消息/方法调用；封装 |
| **Layered 分层** | 多层；**只与相邻层**交互 |
| **Repository 仓库** | **中心共享数据** + 多个计算进程访问 |
| **Blackboard 黑板** | 共享黑板 + **知识源**；状态驱动；无确定算法 |
| **Interpreter 解释器** | 解释引擎 + 代码区/数据区；虚拟机类 |
| **Implicit Invocation 隐式调用** | **事件**注册；发布者不知接收方 |
| **Communicating Processes 进程通信** | 进程间**显式消息**；点对点 |

**样题原题方向：**

- 某图 → Blackboard / Repository / Implicit invocation / Layered？（看清是**知识源+黑板**还是**中心库+多进程**还是**事件**）
- 另一图 → 同上，不要与 Pipe-Filter 混淆（过滤器是线性数据变换，不是知识源）

**易混对比：**

- **Repository vs Blackboard**：都有共享数据；Repository 偏**信息中心/数据库**；Blackboard 偏**非确定性推理、多领域知识协作**。
- **Pipe-Filter vs Batch**：都有数据流；Batch **步骤强顺序、数据整块**；Pipe **过滤器独立、可增量/并发**。

### 1.2 Tactics 与质量属性（单选高频）

**原则：问 “achieve **Availability**” 选可用性战术，别选 Hide information（可修改性）、Introduce concurrency（性能）等。**

| 质量属性 | 正确 Tactics（常考） | 干扰项（勿选） |
|----------|----------------------|----------------|
| **Availability 可用性** | Heartbeat、Ping/Echo、Passive/Active redundancy、Rollback、Exception、Process monitor、Removal from service | Hide information、Introduce concurrency、Authenticate users |
| **Modifiability 可修改性** | Semantic coherence、Use an intermediary、Anticipate expected changes、Maintain existing interface、Configuration files | Heartbeat、Authenticate users、Fixed-priority scheduling |
| **Performance 性能** | Introduce concurrency、Increase resources、Fixed-priority scheduling、Limit execution time、Manage event rate | Ping/Echo（可用性）、Limit access（安全） |
| **Security 安全** | Authenticate users、Authorize、Maintain confidentiality/integrity、Limit access/exposure、Intrusion detection | Heartbeat、Rollback、Record/playback |
| **Testability 可测试性** | Record/playback、Built-in monitors、Separate interface from implementation、Specialized access routines | Maintain data confidentiality、Heartbeat |
| **Usability 易用性** | Maintain user/task/system model、MVC、Undo/Cancel、Aggregate commands | （少用基础设施类战术） |

**2020 真题风格单选答案逻辑：**

1. Availability 不能选：B Semantic coherence（可修改性）
2. Modifiability：C Semantic coherence ✓
3. Performance：D Fixed-priority scheduling ✓
4. Security：B Authenticate users ✓
5. Testability：B Record/playback ✓

**样题：** Availability 选 **B) Heartbeat**（A Hide information、D Introduce concurrency 均为错项）。

### 1.3 UML 认图与选图

**认图（给图选类型）：**

| 图 | 作用关键词 |
|----|------------|
| **Class 类图** | 静态结构、类与关系 |
| **Object 对象图** | 某时刻对象实例快照 |
| **Component 构件图** | 物理/逻辑构件及依赖 |
| **Package 包图** | 包层次、模块组织 |
| **Sequence 顺序图** | **随时间**对象间消息交互 |
| **Communication 通信图** | 协作关系（强调连接） |
| **Activity 活动图** | 活动流、**并行**分支 |
| **State 状态图** | 状态 + 转移条件 |
| **Use case 用例图** | **外部视角**、功能与参与者 |
| **Deployment 部署图** | 软硬件部署 |

**选图（给场合选图）：**

- 外部功能描述 → **Use case**
- 对象随时间交互 → **Sequence**
- 系统静态 backbone → **Class**
- 并行活动 → **Activity**
- 部署到节点 → **Deployment**

**样题陷阱：** 选项里两个 “D)” 是排版错误，按 **Component diagram** 理解构件图题。

## 题型二：简答题

### 2.1 质量属性场景（Quality Attribute Scenario）

**定义（必背英文+中文）：**  
质量属性场景 = 系统如何响应某一刺激的**简短陈述**（stimulus + response + measure）。

**六要素（考试写全即满分）：**

| 要素 | 英文 | 含义 |
|------|------|------|
| 刺激源 | Source | 产生刺激的实体（用户、攻击者、管理员、时钟…） |
| 刺激 | Stimulus | 到达系统的事件/条件 |
| 环境 | Environment | 刺激发生时的系统状态（正常运行、开发时、过载…） |
| 制品 | Artifact | 被影响的部分（整个系统、DB、UI…） |
| 反应 | Response | 系统应采取的活动 |
| 反应度量 | Response Measure | 可测量的指标（时间、比例、次数…） |

**答题模板（1 句话场景）：**  
在 **[Environment]** 下，**[Source]** 产生 **[Stimulus]**，作用于 **[Artifact]**，系统应 **[Response]**，并以 **[Response Measure]** 度量。

**例题（样题第 1 题）：**  
Quality attribute scenario is a concise description of how the system responds to a stimulus. It consists of six parts: source, stimulus, environment, artifact, response, and response measure. For example, during normal operation, an end user sends a page request to the web server; the system should return the page within 1 second.

---

### 2.2 描述某架构风格（如 Blackboard）

**答题结构（四点齐全）：**

1. **定义/组成**：构件类型 + 连接件 + 约束/控制结构  
2. **适用场合**  
3. **优点**（3～5 条）  
4. **缺点**（3～5 条）

**Blackboard 标准答案要点：**

- **构件**：Knowledge source（知识源）、Blackboard（共享数据）  
- **连接**：直接访问共享数据；控制由**黑板状态**驱动  
- **适用**：无单一算法可解、需多领域知识协作、不确定性问题  
- **优点**：知识源可复用、易扩展、适合非确定性、可并行  
- **缺点**：数据一致性难、测试难、开销大、需同步/加锁、对共享结构修改困难  

其他风格见 [架构风格速查表](#架构风格速查表必背)。

## 题型三：设计大题（核心拿分）

### 3.1 需求分析四问（约 30～34 分/题）

**固定四问（样题、2020 真题一致）：**

| 小问 | 要求 | 得分技巧 |
|------|------|----------|
| **a)** | 从需求条目中**识别并命名**质量属性 | 每条需求至少对应 1 个 QA，不要漏“测试/易用” |
| **b)** | 每个 QA 写 **General Scenario**（六要素） | 用英文模板 + 具体数字（需求里的 ms、s、%） |
| **c)** | 每个 QA 至少 **2 个 tactics/solutions** | 从课件“运行时/设计时战术”表抄，别张冠李戴 |
| **d)** | 推荐 **架构风格** + 理由 + 优缺点 | 结合“可变业务规则/分层/事件”选题 |

**需求编号 → 质量属性 速查：**

| 需求关键词 | 质量属性 |
|------------|----------|
| 响应时间、延迟、吞吐、1 小时内扫完、0.1s 登录 | **Performance** |
| 宕机、恢复时间、断电切换、99.99%、年不可用 <10h | **Availability** |
| 远程仅授权、防火墙、加密、审计、密码规则、交易安全 | **Security** |
| 改 UI 人天/人周、换传感器 3 天、minor update 1 天 | **Modifiability** |
| 界面友好、易学、仿微博 | **Usability** |
| 测试接口、代码覆盖率、可远程调试 | **Testability** |
| 价格 $199、工期 3 个月 | 常作**业务约束**，可不单独算 QA，或归 Modifiability/Performance 边界 |

**扫地机器人（样题 ○1）参考映射：**

| 需求 | QA |
|------|-----|
| 0.5cm 障碍 0.1s 越过 | Performance |
| 故障恢复 <5min | Availability |
| 远程仅授权控制 | Security |
| 测试接口 | Testability |
| 换传感器 3 天更新 | Modifiability |
| 低电量自主回充 | Availability / 功能 |
| 20㎡ <1h 扫完 | Performance |
| UI 简单友好 | Usability |

**推荐风格（d 问）：**  
**分层（Layered）+ 面向对象**：传感器/行走/清扫/ UI 分层；核心模块协调。  
或 **隐式调用**：传感器事件驱动清扫。  
**理由**：需求强调模块替换（可修改）、核心协调（分层清晰）。  
**优点**：易维护、模块可换；**缺点**：层间调用开销、实时性需额外优化。

**企业微博（样题 ○2）：**  
QA：Availability(2,3)、Usability(4)、Modifiability(5)、Security(6,7)、Performance(8)、Testability(9)。  
风格：**隐式调用 / 事件驱动**（部门发消息 → 通知所有 follower）或 **分层 + 仓库**（信息中心存 feed）。

**MSM 会员/Golf（样题 ○3）：**  
折扣规则**常变、等级可扩展** → **Modifiability** 最重要；推荐 **Rule-based（规则系统）** 或 **面向对象 + 策略模式**。  
课件提示：规则系统 **逻辑与数据分离**；缺点：规则不透明、搜索慢。

**GO IDE（样题 ○4）：**  
编译 0.01s → Performance；远程诊断 → Testability/Modifiability；拼写检查、外观 → Usability；2 月移植 → Modifiability/Portability。  
风格：**分层（UI / 编译 / 调试）** 或 **虚拟机/解释器**（若强调交互式增量编译）。

**SMMS 超市会员（2020 真题）：**  
g 审计恢复 → Security + Availability；e 1s 交易 → Performance；d 外部意外消息不停机 → Availability；c UI 2 天 → Modifiability；f 易用 → Usability；b 覆盖率 → Testability。  
**推荐：Rule-based 或 OO**（折扣规则多变、等级扩展）。

### 3.2 效用树 Utility Tree（约 16 分）

**结构（四层，必须画树）：**

```
[质量属性] — H/M, H/M
  └─ [细化属性] — H/M, H/M
       └─ [具体场景描述] — (重要性 H/M/L, 实现难度 H/M/L)
```

**六大质量属性子节点（参考材料 + 复习笔记）：**

| 根节点 | 常见子节点 | 场景举例 |
|--------|------------|----------|
| **Performance** | latency, throughput, response time, capacity | 实时视频 <3s；DB 延迟 300ms/200ms；1GB 视频 <10s |
| **Security** | confidentiality, integrity, authorization | 实名认证；交易 99.999%；密码 16 位；授权库 99.99% |
| **Availability** | failure, data loss, recovery | 断电 5min 内切站；网络故障 <1.5min 恢复；DB 99.99% |
| **Modifiability** | add/delete/change UI, middleware, client | 中间件 <10 人月；改 Web UI <4 人周；新 Android 客户端 <2 人周 |
| **Usability** | learn, efficient use, error impact, comfort | 扁平 UI；Windows 外观；易学 |
| **Testability** | （有时单独列） | 局域网远程调试；测试接口 |

**样题场景归类示例（智能视频监控 ○1）：**

| 编号 | 场景 | 归类 |
|------|------|------|
| 3 | 实时视频 <3s | Performance → latency/response time |
| 4 | 断电 site1→site3 <5min | Availability → recovery |
| 5 | 实名认证服务器 | Security → authentication |
| 6 | 加中间件 <10 人月 | Modifiability → add middleware |
| 7 | 视频 DB 300ms | Performance → latency |
| 8 | 授权库 99.99% | Availability 或 Security |
| 9 | Web UI 改扁平 <10 人周 | Modifiability → change UI |
| 12 | 网络故障 <1.5min | Availability → detect/recover |
| 11 | 新 Android 客户端 <2 人周 | Modifiability |

**画图注意：** 每个叶节点写 **(H,M)** 或 **(M,L)** 表示重要性与实现难度；老师可能不扣分权重，但**树形完整**才满分。

### 3.3 架构评估四概念（约 20 分）

**先写定义（各 1～2 句），再判 a～f：**

| 概念 | 定义（中文） | 识别口诀 |
|------|--------------|----------|
| **Risk 风险** | 可能**损害**某质量属性的设计决策 | “无法检测”“规则不清”“可能导致…” |
| **Non-risk 非风险** | **良好**决策，有助于实现目标 | 假设合理、指标已论证、设计稳妥 |
| **Sensitivity point 敏感点** | 方案中**微小变化**就显著影响**某一**质量属性 | “数量/并发/位数 **影响** 吞吐量/性能” |
| **Tradeoff 权衡点** | **一个决策影响多个**质量属性 | “encryption 影响 security **and** performance” |

**样题判题答案参考：**

| 描述 | 答案 |
|------|------|
| a) 无法检测 server-client 通信线故障 | **Risk** |
| b) 并发连接数显著影响 DB 每秒事务数 | **Sensitivity** |
| c) 改加密算法影响安全与性能 | **Tradeoff** |
| d) 采样 1 次/秒、处理 <30ms → 1s 软截止合理 | **Non-risk** |
| e) VIP 折扣政策不清 → 功能重复 | **Risk** |
| f) 高模块化可能降低可移植性与性能 | **Tradeoff** |

| 描述（○2/2020） | 答案 |
|-----------------|------|
| login 方式影响安全与性能 | **Tradeoff** |
| 存款业务流程规则不清 | **Risk** |
| 维护人天对封装程度敏感 | **Sensitivity** |
| 消息率+处理时间 → 1s 截止合理 | **Non-risk** |
| 第三方组件无法检测故障 | **Risk** |
| 加密算法与加密位数相关 | **Sensitivity** |

## 架构风格速查表（必背）

| 风格 | 构件 | 连接件 | 适用 | 优点 | 缺点 |
|------|------|--------|------|------|------|
| Batch Sequential | 数据变换程序 | 数据流 | 编译器、CASE、可分解为步骤 | 隐蔽性好、易分析吞吐 | 交互差、无标准、同步难 |
| Pipe-Filter | 过滤器 | 管道 | 编译、多媒体、增量处理 | 并发、重用、易维护 | 交互差、性能、同步 |
| Main/Subroutine | 过程+数据 | 过程调用 | 结构化算法 | 逐步分解 | 难并行、结构不清晰 |
| OO | 对象 | 消息/调用 | 界面与实现分离 | 封装、易理解 | 耦合、性能、对象过多 |
| Layered | 层内构件 | 层协议 | 服务可分层 | 分解问题、修改局部 | 性能、层数难定 |
| Repository | 内存+计算进程 | 访问/调用 | 复杂信息中心 | 数据集中 | 瓶颈、同步 |
| Blackboard | 知识源+黑板 | 访问黑板 | 不确定、AI、多专家 | 可扩展、知识复用 | 一致性、测试难、开销 |
| Interpreter | 引擎+存储区 | 访问/调用 | 无原生语言、脚本 | 模拟、灵活 | 效率低、需验证 |
| Rule-based | 规则库+推理机 | 匹配 | 专家系统、折扣规则 | 知识/控制分离 | 规则不透明、慢 |
| Communicating Processes | 进程 | 消息 | 独立计算集合 | 并行、隔离 | 配置复杂 |
| Implicit Invocation | 发布进程 | 事件绑定 | 松耦合、GUI、中间件 | 易插拔、重用 | 失控、顺序不确定、调试难 |

## 质量属性与 Tactics 速查

### 六要素通用场景（背诵表头即可）

详见参考材料：Usability / Security / Testability / Availability / Modifiability / Performance 的 Source–Stimulus–Artifact–Environment–Response–Measure。

### 刺激（Stimulus）一词对应

| QA | Stimulus 关键词 |
|----|-----------------|
| Availability | 意外事件、预期事件未发生 |
| Modifiability | add/delete/change/vary 功能、平台、QA、容量 |
| Performance | periodic / sporadic / stochastic 事件 |
| Security | display/modify/delete/access/denial of service |
| Testability | 开发阶段完成、系统交付 |
| Usability | learn / use efficiently / minimize errors / adapt / comfortable |

### Tactics 分类（简答/设计 c 问）

**Availability：** 错误检测（Ping/Echo、Heartbeat、Exception）→ 恢复（投票、主备冗余、Checkpoint/Rollback）→ 预防（进程监视、事务）

**Security：** 抵抗攻击（认证、授权、机密性、完整性、限制暴露/访问）→ 检测攻击 → 恢复

**Performance：** 控制资源需求（提高效率、管理事件率、限制时间/队列）→ 资源管理（并发、多副本、加资源）→ 仲裁（FIFO、固定/动态优先级调度）

**Modifiability：** 局部化修改（语义一致、预期变更、泛化模块）→ 防止连锁（信息隐藏、维持接口、适配器）→ 推迟绑定（运行时注册、配置文件、多态）

**Usability：** 运行时模型（用户/任务/系统模型）；设计时 MVC、Seeheim 等

**Testability：** 输入/输出捕获、内置监视、专用测试接口
