# Question 1：Stakeholders and Scrum Roles（10 分）

## 1.1 题目要求

- Identify **key stakeholders**（从案例描述中提取）
- **Map** given project team → Scrum roles（PO / SM / Dev Team / Stakeholders）
- **Explain** responsibility of each Scrum role

## 1.2 必背知识点

### Scrum 三角角色（Scrum Team = 3 角色，不是 4）

| 角色 | 人数 | 核心职责（英文关键词） |
|------|:----:|----------------------|
| **Product Owner (PO)** | 1 | Own backlog · Prioritize · Accept/reject increments · Maximize value |
| **Scrum Master (SM)** | 1 | Facilitate Scrum events · Remove impediments · Coach team · Protect team |
| **Development Team** | 5–9 | Cross-functional · Self-organizing · Deliver shippable increment each Sprint |

> **Stakeholders 不是 Scrum Team 成员**，但必须在 Q1 中单独列出。

### 给定团队 → Scrum 映射（两案例通用）

| 案例给定职位 | 映射到 |
|-------------|--------|
| Project Manager / Scrum Master | **Scrum Master** |
| Product Owner / Client Representative | **Product Owner** |
| Business Analyst | **Development Team** |
| UI Designer | **Development Team** |
| Developer (×2) | **Development Team** |
| Tester | **Development Team** |
| Database Administrator | **Development Team** |

### 干系人识别模板

从案例描述中找这些关键词 → 对应干系人：

| 关键词 | 干系人 |
|--------|--------|
| 大学管理层 / written final approval | University Management |
| 馆长 / 经理 | Chief Librarian / Canteen Manager |
| 一线工作人员 | Library Staff / Canteen Staff |
| 学生、教师 | Students, Faculty Members |
| IT / 托管 | IT Department, Hosting Provider |
| 支付（Case2） | Payment Service Provider |

## 1.3 满分答题结构

```
① Key Stakeholders（列表，8–11 个）
② Scrum Role Mapping（表格：Scrum Role | Project Role | Responsibility）
③ Explanation（2–4 句：为什么 PO 是馆长/经理代表，SM 是 PM，Dev Team 包含谁）
```

## 1.4 Case1 标答要点

- PO = **Chief Librarian or Client Representative**（代表图书馆业务需求）
- SM = **Project Manager**（流程 facilitation + 消除障碍）
- Dev Team = BA + UI + 2 Dev + Tester + DBA
- Stakeholders = Students, Faculty, Library Staff, Management, IT, Hosting Provider

## 1.5 扣分点

- 把 Stakeholder 和 Scrum Team 混为一谈
- 漏写 Development Team 的具体组成
- 只列名字不解释职责
- PO 写成 Developer 或 SM 写成 PO

# Question 2：Product Backlog（15 分）

## 2.1 题目要求

- ≥ **10 个** Product Backlog Items（PBI）
- **Prioritized**（必须有优先级编号）
- Explain **reason for top 5 priorities**

## 2.2 必背知识点

### 什么是 Product Backlog

- PO 拥有的、**按优先级排序**的需求列表
- 包含功能、修复、技术工作、知识获取等
- **Living document** — 持续 refinement，不是一次性写死

### 优先级排序逻辑（满分理由框架）

| 优先级 | 一般原则 | 案例应用 |
|:------:|---------|---------|
| 1 | **安全/访问基础** — 没有登录，其他功能无法使用 | Secure login & RBAC |
| 2 | **核心用户价值** — 直接解决案例描述的痛点 | Book search / Menu browse |
| 3 | **核心交易/操作** — 系统存在的根本目的 | Reservation / Order placement |
| 4 | **减少人工/错误** — 案例中明确提到的问题 | Fine calc / Order tracking |
| 5 | **一线人员工作流** — 使前端功能可被履行 | Staff issue-return / Kitchen dashboard |

### PBI 写法规范

```
Priority | PBI ID | Product Backlog Item | Reason（Top 5 需详细写）
```

- 每条 PBI = **一个可交付的功能单元**（不是"Sprint 1 的工作"）
- 用案例描述中的 **feature 列表** 做基础，拆细到 10–12 条
- 末尾加 **Training / Documentation / Deployment / UAT** 类 PBI

## 2.3 Case1 标准 Backlog（12 条）

| Pri | PBI | Top 5 理由 |
|:---:|-----|-----------|
| 1 | Secure login & RBAC | 所有用户必须先安全访问 |
| 2 | Book catalogue browsing | 用户需在线查看图书 |
| 3 | Book search | 解决"必须亲自到馆找书"的痛点 |
| 4 | Book reservation | 学生/教师在线预约 |
| 5 | Book renewal | 减少人工续借工作 |
| 6 | Book issue processing | 工作人员借出管理 |
| 7 | Book return processing | 归还记录准确 |
| 8 | Borrowing status tracking | 跟踪借还状态 |
| 9 | Automatic fine calculation | 减少人工罚款错误 |
| 10 | Report generation | 管理层快速出报表 |
| 11 | Administrator dashboard | 系统管理 |
| 12 | User training & help documentation | 上线前必需 |

## 2.4 Case2 标准 Backlog（12 条）

| Pri | PBI | Top 5 理由 |
|:---:|-----|-----------|
| 1 | Secure login & RBAC | 安全基础 |
| 2 | Menu browsing & food search | 核心发现功能 |
| 3 | Cart & order placement | 核心商业目标 |
| 4 | Order status tracking | 解决排队/状态不可见 |
| 5 | Order preparation dashboard | 厨房履行订单 |
| 6 | Pay at counter | MVP 支付路径 |
| 7 | Online payment integration | 完整支付 |
| 8 | Inventory / availability update | 减少浪费 |
| 9 | Sales report generation | 管理层报表 |
| 10 | Administrator dashboard | 系统 oversight |
| 11 | Staff training programme | 验收条件 |
| 12 | Deployment & UAT | 上线 |

## 2.5 扣分点

- 不足 10 条
- 没有优先级编号
- Top 5 理由与案例痛点无关（泛泛而谈）
- PBI 粒度太粗（"开发整个系统"）或太细（"写第 3 行代码"）

# Question 3：User Stories and Acceptance Criteria（15 分）

## 3.1 题目要求

- **6 条** User Stories
- 覆盖案例指定的**所有用户角色**
- 为**任意 3 条**写 Acceptance Criteria

## 3.2 必背知识点

### User Story 三段式（必须用这个模板）

```
As a [role],
I want to [action/feature],
So that [benefit/value].
```

### 角色覆盖检查清单

| Case1 OLMS | Case2 食堂 |
|------------|-----------|
| Student ✓ | Student ✓ |
| Faculty ✓ | Faculty ✓ |
| Library Staff ✓ | Canteen Staff ✓ |
| Administrator ✓ | Canteen Manager ✓ |
| — | Administrator ✓ |

> Case1 要求 4 类角色各至少 1 条；Case2 要求 5 类。6 条故事要**均匀覆盖**。

### Acceptance Criteria 写法

| 格式 | 示例 |
|------|------|
| **Given-When-Then** | Given I am logged in as student, when I search "Java", then matching books are displayed |
| **清单式** | User can search by title, author, keyword · System shows availability · Access denied for unauthorized roles |

### 好 AC 的 4 个特征

1. **可测试** — 改卷人能判断 pass/fail
2. **具体** — 提到字段、按钮、状态
3. **含权限** — 至少 1 条 AC 测 role-based access
4. **含边界** — 不可用/未登录/无数据时的行为

## 3.3 Case1 六条故事模板

| # | Role | Story 摘要 |
|---|------|-----------|
| 1 | Student | Search books online without visiting library |
| 2 | Faculty | Reserve books online for academic resources |
| 3 | Student | Renew borrowed books online |
| 4 | Library Staff | Issue and return books with accurate records |
| 5 | Library Staff | Automatic fine calculation |
| 6 | Administrator | Generate reports for management |

## 3.4 Case1 三条 AC 示例（官方标答）

**US-1 Book Search**
- Search by title, author, keyword
- Display matching books
- Show availability status

**US-2 Book Reservation**
- Logged-in student/faculty can reserve available book
- System confirms reservation
- Staff can view reservation record

**US-3 Automatic Fine Calculation**
- Calculate fine based on due date and return date
- Display fine amount correctly
- Staff can verify before closing transaction

## 3.5 扣分点

- 没有用 As a / I want / So that 格式
- 6 条故事角色覆盖不全（如 6 条全是 Student）
- AC 太模糊（"system works well"）
- 只写 3 条故事或 AC 不足 3 条

# Question 4：Sprint Plan and Product Increment（15 分）

## 4.1 题目要求

- **8 Sprint**（Sprint 0 → Sprint 7）
- 4 个月，每 Sprint **2 周**
- 每个 Sprint 写：**Sprint Goal · Selected Backlog Items · Expected Product Increment**

## 4.2 必背知识点

### Sprint 时间结构

```
Sprint 0 (Week 1–2)  : 启动，不做功能开发
Sprint 1–6 (Week 3–14): 功能增量交付
Sprint 7 (Week 15–16): 测试 + 培训 + 部署 + 验收
```

### Sprint 0 必含内容

- Stakeholder discussion
- Scrum role confirmation
- Initial Product Backlog + prioritization
- Development / test / DB environment setup
- **Increment** = Prioritized backlog + project setup ready（不是可运行软件）

### 每个 Sprint 的 Increment 必须是

- **Usable** — 可演示、可 Review
- **Potentially shippable** — 满足 Definition of Done
- **对应 Sprint Goal** — 不能 Goal 写 A 但 Increment 交付 B

### Sprint 规划原则

| 原则 | 说明 |
|------|------|
| 依赖顺序 | Login → Browse → Search → Transaction → Staff ops → Admin/Reports → Release |
| 递增价值 | 越早 Sprint 交付用户可见功能 |
| 1 Sprint = 1 Goal | Goal 用一句话概括本 Sprint 主题 |
| Sprint 7 不开发新功能 | 聚焦 UAT / Training / Deployment / Approval |

## 4.3 Case1 Sprint 计划（官方标答）

| Sprint | Goal | Backlog Items | Increment |
|:------:|------|---------------|-----------|
| 0 | Prepare foundation | Stakeholder discussion, roles, backlog, env | Prioritized backlog + setup done |
| 1 | Basic access | Login, RBAC | Users log in by role |
| 2 | Catalogue access | Catalogue browse, book details | Browse catalogue online |
| 3 | Book discovery | Search, filter, availability | Search books + check availability |
| 4 | User transactions | Reservation, renewal | Students/faculty reserve & renew |
| 5 | Staff operations | Issue, return, status tracking | Staff issue/return/track books |
| 6 | Fine, reports, admin | Fine calc, reports, admin dashboard | Fines + reports + dashboard working |
| 7 | Final release | Integration test, UAT, training, deploy, approval | Release-ready system + trained users |

## 4.4 Case2 Sprint 计划

| Sprint | Goal | Increment |
|:------:|------|-----------|
| 0 | Initiation | Backlog + environment ready |
| 1 | Secure access | Login for all roles |
| 2 | Menu discovery | Browse & search menu |
| 3 | Core ordering | Place orders + pay at counter |
| 4 | Order fulfilment | Status tracking + staff dashboard |
| 5 | Online payment | Payment gateway integrated |
| 6 | Management | Inventory + reports + admin dashboard |
| 7 | Release | Production live + staff trained + approval |

## 4.5 扣分点

- 只有 7 个 Sprint 或 Sprint 编号从 1 开始
- Increment 太抽象（"progress made"）
- Sprint 0 写了功能开发
- 每个 Sprint 没有 Goal 或没有对应 PBI

# Question 5：Scrum Based Work Breakdown Structure（15 分）

## 5.1 题目要求

- **Hierarchical tree structure**（层级树，不是表格）
- Explain how WBS connects with **Product Backlog · Sprint Plan · Schedule · Deliverables**

## 5.2 必背知识点

### Scrum WBS vs 传统 WBS

| 传统 WBS | Scrum WBS |
|---------|-----------|
| 按阶段/交付物分解 | 按 **Sprint + 功能模块** 分解 |
| 底层 = 工作包 | 底层 = Sprint 内的具体任务包 |
|  Often includes 1.1 PM activities | 通常含 1.1 Scrum ceremonies |

### 推荐树结构（两案例通用）

```
1.0 [Project Name]
├── 1.1 Scrum Project Management
│   ├── Sprint Planning / Daily Scrum / Review / Retrospective / Backlog Refinement
├── 1.2 Sprint 0: Project Initiation
│   ├── Stakeholders / Roles / Backlog / Environment
├── 1.3 Sprint 1: [Theme]
│   ├── [Feature tasks] + Sprint Review
├── 1.4 Sprint 2: [Theme]
│   └── ...
...
└── 1.9 Sprint 7: Release Preparation
    ├── UAT / Training / Documentation / Deployment / Approval
```

### WBS 与其他 artifact 的关系（必写段落）

```
Product Backlog  →  identifies ALL work
       ↓
Sprint Plan      →  selects items per Sprint
       ↓
Scrum WBS        →  breaks Sprint work into work packages
       ↓
Schedule         →  places work across 4 months (8 × 2 weeks)
       ↓
Product Increment →  deliverable at end of each Sprint
       ↓
Final Accepted System
```

**每步一句话解释**，官方标答就是这个链条。

### WBS 100% 规则

- 所有 Sprint 的工作加总 = 整个项目范围
- 每个 Sprint 节点下至少 3–5 个叶子任务
- 每个 Sprint 末尾含 **Sprint Review and feedback**

## 5.3 扣分点

- 用列表代替树形结构
- 没有 Sprint 0 或 Sprint 7
- 没解释 WBS 与 Backlog/Sprint 的关系
- WBS 与传统阶段混用（Requirements / Design / Coding 三阶段）

# Question 6：Earned Value Management（15 分）

## 6.1 题目要求

计算 **PV · EV · AC · SV · CV · SPI · CPI**  
解释：**ahead or behind schedule · under or over budget**  
提出：**Scrum Master 和 PO 的 corrective actions**

## 6.2 必背公式（默写）

| 指标 | 公式 | 判断 |
|------|------|------|
| **PV** | Planned % × BAC | — |
| **EV** | Actual % × BAC | — |
| **AC** | 题目给定 | — |
| **SV** | EV − PV | <0 落后 · >0 提前 |
| **CV** | EV − AC | <0 超支 · >0 节约 |
| **SPI** | EV / PV | <1 慢 · >1 快 |
| **CPI** | EV / AC | <1 成本差 · >1 成本好 |
| **EAC** | BAC / CPI | （补充，展示深度） |

### Scrum EVM vs 传统 EVM（Task1）

| | Scrum（Case1/2） | 传统（Task1） |
|---|-----------------|--------------|
| 计量单位 | Sprint 完成百分比 | 各活动完成 % × 预算 |
| PV | 50% × BAC | 各活动计划% × 活动预算，再求和 |
| 粒度 | 项目整体 | 分活动 A–E 分别算再汇总 |
| 工期预测 | 可选 | 原工期 / SPI |

## 6.3 Case1 完整计算

```
BAC = 55,000
PV  = 55,000 × 0.50 = 27,500
EV  = 55,000 × 0.45 = 24,750
AC  = 29,000
SV  = 24,750 − 27,500 = −2,750  → Behind Schedule
CV  = 24,750 − 29,000 = −4,250  → Over Budget
SPI = 24,750 / 27,500 = 0.90
CPI = 24,750 / 29,000 = 0.85
EAC = 55,000 / 0.85 = 64,706
```

## 6.4 Case2 完整计算

```
BAC = 60,000
PV  = 60,000 × 0.50 = 30,000
EV  = 60,000 × 0.48 = 28,800
AC  = 32,000
SV  = 28,800 − 30,000 = −1,200  → Behind Schedule
CV  = 28,800 − 32,000 = −3,200  → Over Budget
SPI = 28,800 / 30,000 = 0.96
CPI = 28,800 / 32,000 = 0.90
EAC = 60,000 / 0.90 = 66,667
```

## 6.5 状态解释模板（英文）

**Schedule:**
> SV is negative and SPI is less than 1 (0.90), therefore the project is **behind schedule**. Only [45/48]% of planned work has been completed vs 50% planned.

**Cost:**
> CV is negative and CPI is less than 1 (0.85), therefore the project is **over budget**. For every USD 1 spent, only USD 0.85 of value is earned.

## 6.6 纠正措施（SM + PO 分工）

| Scrum Master | Product Owner |
|-------------|---------------|
| Facilitate Sprint Retrospective to find blockers | Re-prioritize backlog — defer low-value items |
| Track burndown / velocity each Sprint | Clarify acceptance criteria to reduce rework |
| Remove impediments | Report EVM status to management |
| Protect Sprint scope from mid-Sprint changes | Negotiate scope/budget with management |
| Use Daily Scrum to detect delays early | Control change requests through backlog |
| Coach team on estimation accuracy | Decide trade-offs when adding new features |

## 6.7 扣分点

- 公式写错（SV = PV − EV）
- 百分比用小数还是整数算错（50% = 0.50）
- 只算数字不写 behind/over 结论
- 没写 corrective actions 或 SM/PO 不区分

# Question 7：Risk and Change Management（15 分）

## 7.1 题目要求

- Identify **5 major risks**
- Explain how **Scrum helps manage** each
- Handle a **specific change request** after Sprint 4
- Explain impact on **Backlog · Sprint Planning · Cost · Schedule · PO decision**

## 7.2 必背知识点

### 风险登记表结构

| # | Risk | Type | Impact | Scrum Response |
|---|------|------|--------|----------------|

### 案例通用五大风险（换项目名即可）

| # | 风险 | Scrum 应对机制 |
|---|------|---------------|
| R1 | 用户看到增量后要求新功能（Scope creep） | Backlog refinement · PO prioritization · Fixed Sprint length |
| R2 | 4 个月内无法完成（Schedule） | Sprint Planning · Daily Scrum · Sprint Review 监控进度 |
| R3 | 成本超过 BAC（Cost） | PO 控制优先级 · 限制变更 · EVM 监控 |
| R4 | 一线人员不会用系统（Usability） | Sprint Review 邀请真实用户 · UAT · 培训 Sprint |
| R5 | 数据不完整/集成失败（Technical） | 早期 Increment 验证 · Definition of Done · 尽早集成 |

### Scrum 管理风险的 6 个机制（必背）

1. **Small increments** — 降低大爆炸交付风险
2. **Sprint Review** — 早期 stakeholder 反馈
3. **Daily Scrum** — 及早发现 blockers
4. **Backlog Refinement** — 有序管理变更
5. **Definition of Done** — 保证质量
6. **Sprint Retrospective** — 持续改进

### 变更处理 7 步流程（Case1 条码 / Case2 预购 通用）

```
① Stakeholder submits request → Product Owner（不是直接找 Developer）
② PO + Dev Team estimate effort in Backlog Refinement
③ PO adds new PBI to Product Backlog
④ PO compares value vs existing items → re-prioritize
⑤ Select for future Sprint in Sprint Planning（不打断当前 Sprint）
⑥ If budget/schedule affected → remove/postpone lower-priority items
⑦ Deliver in Sprint Review → stakeholder inspects
```

### 变更影响分析（表格必写）

| Area | Impact |
|------|--------|
| Product Backlog | New PBI added; lower-priority items may be deferred |
| Sprint Planning | Selected for Sprint 5/6/7 based on capacity |
| Cost | Additional dev/test effort → AC increases |
| Schedule | May delay other features or extend timeline |
| PO Decision | Trade-off: add vs defer vs Phase 2 vs reject |

### 满分 PO 决策句型

> Given CPI = [X] and SPI = [Y], the PO should add the feature to the backlog but **only implement it if a lower-priority item is removed**, or seek **additional budget/时间 extension** from management. Otherwise, defer to **Phase 2** post-launch.

## 7.3 Case1 变更：Barcode Scanning

- Library staff request after Sprint 4
- Add PBI to backlog → estimate → prioritize against existing items
- May replace lower-priority admin extras in Sprint 6/7
- Do NOT disturb current Sprint unless urgent + PO approved

## 7.4 Case2 变更：Pre-order by Time Slot

- Students request after Sprint 4 to reduce queue waiting
- Same 7-step process
- With CPI=0.90, SPI=0.96 already behind/over → PO must trade off scope

## 7.5 扣分点

- 风险不足 5 条
- 没解释 Scrum 如何帮助（只列风险）
- 变更直接加入当前 Sprint（错误）
- 没分析对 Backlog/Cost/Schedule 的影响

# 附录 A：Scrum 术语速查卡

| 术语 | 含义 |
|------|------|
| Product Backlog | PO 拥有的优先级需求列表 |
| Sprint Backlog | 当前 Sprint 选中的 PBI + 实现计划 |
| Product Increment | 每个 Sprint 结束时的可用增量 |
| Definition of Done | 增量完成的统一标准 |
| Sprint Goal | 本 Sprint 要达成的目标 |
| Velocity | 团队每 Sprint 完成的工作量 |

## B.1 WBS 知识点

- **100% 规则** · 按可交付成果 · 3–4 层 · 叶子 = 活动

## B.2 Gantt 知识点

- 列：活动 | 前置 | 工期 | 开始 | 结束
- Forward scheduling：ES = max(前置 EF)
- 关键路径活动加粗

## B.3 Cost 知识点

- 总预算 = 工期 × 日成本
- BAC = 各活动预算之和 = **3350**
- 成本基线 = 按时间累计 PV

## B.4 CPM 知识点

|------|----|----|----|----|-----|------|

| C | 5 | 9 | 6 | 10 | 1 | ✗ |
| D | 5 | 8 | 5 | 8 | 0 | ✓ |

## B.5 EVM 知识点（Task1 第 8 天）
